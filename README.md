# IoT ฟอร์จูน — ติดตามระบบอาคารตามจุด

ต้นแบบเว็บแอป (ฝั่งหน้าเว็บอย่างเดียว) สำหรับติดตามจุดตรวจวัด IoT ในอาคารฟอร์จูนทาวน์ แสดงโมเดลห้างจำลองแบบ 3D บนโต๊ะไม้ในห้องทดลอง และผังชั้น 2D ที่เลือกจุดได้ ช่างเทคนิคเห็นได้ว่าจุดใดต้องดูแล ดูค่าวัดพร้อมเวลาสังเกตและความสดของข้อมูล ดูแนวโน้ม และรับทราบการแจ้งเตือนพร้อมบันทึก

> **สถานะ:** ต้นแบบ อ่านข้อมูลอย่างเดียว ไม่มีการควบคุมอุปกรณ์ (ไม่มีปุ่มสั่งปั๊ม/เบรกเกอร์)
> จุด IoT 8 จุดและเกณฑ์แจ้งเตือนทั้งหมดเป็น **ตัวอย่าง** ไม่ใช่รายการอุปกรณ์จริงของฟอร์จูน
> รูปทรงอาคารลากจากภาพผังพื้นที่เช่าที่ได้รับ **โดยประมาณ** ไม่ใช่แบบก่อสร้าง

## เริ่มใช้งาน

ต้องมี Node.js 20 ขึ้นไป

```bash
npm install          # ติดตั้งตาม package-lock.json
npm run dev          # โหมดพัฒนา http://localhost:5173
npm test             # ชุดทดสอบ Node test runner
npm run build        # สร้างไฟล์ใช้งานจริงใน dist/
npm run preview      # เปิด dist/ ที่ http://localhost:4173
npm run fixture      # เซิร์ฟเวอร์ทดสอบ API ในเครื่อง http://127.0.0.1:8787/telemetry
```

โฟลเดอร์ `dist/` ใช้เส้นทางไฟล์แบบสัมพัทธ์ จึงวางบนเว็บเซิร์ฟเวอร์ใดก็ได้ (รวมถึงโฟลเดอร์ย่อย) มีสองหน้า:
- `index.html` — แอปหลัก
- `materials.html` — แหล่งที่มา สัญญาอนุญาต และข้อจำกัด

> เปิด `dist/index.html` ตรงจากไฟล์ (file://) ไม่ได้ เพราะเบราว์เซอร์บล็อก ES module — ต้องเปิดผ่านเว็บเซิร์ฟเวอร์ เช่น `npm run preview`

**รุ่นที่ใช้:** three.js `0.180.0`, Vite `6.4.3` (ตรวจแล้วว่ามีใน npm registry และติดตั้งรุ่นนี้ตรงตามที่ขอ), fake-indexeddb `6.2.5` (ใช้ในการทดสอบเท่านั้น)

**ใช้ฐานข้อมูลแยก:** เพิ่ม `?db=ชื่อ` ท้าย URL เช่น `http://localhost:4173/?db=training` จะใช้ IndexedDB ชื่อ `iot-fortune-training` แยกจากข้อมูลปกติ (เหมาะกับการทดสอบ/ฝึกอบรม)

### เมนูหลัก
| เมนู | ใช้ทำอะไร |
|---|---|
| ภาพรวม | โมเดล 3D / ผัง 2D, แผงรายละเอียดจุด, กราฟแนวโน้ม, รายการจุด |
| จุดตรวจวัด | ค้นหาและกรองจุด (ชั้น พื้นที่ ระบบ ระดับ คุณภาพข้อมูล) ใช้ได้ครบแม้ไม่มี 3D |
| แจ้งเตือน | เหตุการณ์ที่ยังไม่ปิด/กำลังเกิด/ทั้งหมด และรับทราบพร้อมบันทึก |
| ประวัติข้อมูล | กราฟ/ตารางย้อนหลังที่บันทึกในเครื่องนี้, ส่งออก CSV, สถิติข้อมูลที่ถูกปฏิเสธ |
| ตั้งค่าจุด | แหล่งข้อมูล, เพิ่ม/แก้ไขจุด, เกณฑ์, นโยบายเก็บข้อมูล, สำรอง/กู้คืน |

ตัวชี้วัด (KPI) ด้านบนกดเพื่อเปิดรายการที่ตรงเงื่อนไขได้:
- **จุดที่ติดตาม** — จุดที่สถานะ active (ไม่รวมจุดเก็บถาวร)
- **จุดที่ต้องดูแล** — จุดที่มีการแจ้งเตือนกำลังเกิด *หรือ* มีค่าวัดใดไม่สดใหม่ (นับจุดละ 1 แม้มีหลายค่าวัด)
- **จุดวิกฤต** — จุดที่มีการแจ้งเตือนระดับวิกฤตกำลังเกิด
- **จุดที่ข้อมูลไม่สดใหม่** — จุดที่มีค่าวัดอย่างน้อยหนึ่งค่า เก่า/ยังไม่มี/ไม่ถูกต้อง
- **แจ้งเตือนยังไม่ปิด** — นับเป็น *เหตุการณ์ระดับค่าวัด* ที่ยังเกิดอยู่ หรือยังไม่ได้รับทราบ

## โหมดแหล่งข้อมูล

| ป้าย | ความหมาย |
|---|---|
| **ข้อมูลจำลอง** | สร้างค่าในเบราว์เซอร์ตามสถานการณ์ ไม่ใช่ข้อมูลจริงของฟอร์จูน มีแถบสีเหลืองแสดงตลอด |
| **ข้อมูลจาก API** | ดึงจาก URL ที่ตั้งค่าไว้ตามสัญญา JSON ด้านล่าง |
| **ข้อมูลเก่า / ขาดการติดต่อ** | แสดงเป็นป้ายคุณภาพของแต่ละค่าวัด (ข้อมูลเก่า, ยังไม่มีข้อมูล, ข้อมูลไม่ถูกต้อง) แยกจากสถานะการเชื่อมต่อ |

- เปลี่ยนโหมดที่ **ตั้งค่าจุด → แหล่งข้อมูล** แล้วกด "บันทึกและเริ่มใช้"
- เปลี่ยนโหมดแล้ว engine และอะแดปเตอร์เดิมถูกปิด สร้างใหม่ทั้งหมด ประวัติของ demo และ api เก็บแยกกัน **ไม่นำค่าจากแหล่งหนึ่งมาเป็นค่าปัจจุบันของอีกแหล่ง**
- เมื่อ API ล้มเหลว **ไม่มีการใช้ค่าจำลองแทน** ค่าสุดท้ายที่ถูกต้องยังแสดงพร้อมเวลาสังเกตจริง และค่อย ๆ กลายเป็น "ข้อมูลเก่า"
- จุดที่ API ไม่ได้ส่งค่ามาจะแสดง "ยังไม่มีข้อมูล"

### ลองโหมด API บนเครื่องตัวเอง
```bash
npm run fixture
```
แล้วตั้งค่า URL เป็น `http://127.0.0.1:8787/telemetry` (อนุญาต http เฉพาะ localhost) fixture ส่งค่าทดสอบของ P-001, P-005, P-008 และเปลี่ยนพฤติกรรมได้:

| คำสั่ง | ผล |
|---|---|
| `curl "http://127.0.0.1:8787/control?mode=normal"` | ค่าปกติ เวลาสังเกตปัจจุบัน |
| `…?mode=stuck` | poll สำเร็จแต่ค่าค้างเวลาเดิม → ค่าวัดกลายเป็น "ข้อมูลเก่า" ทั้งที่การเชื่อมต่อปกติ |
| `…?mode=fail` | ตอบ HTTP 503 → แถบสถานะแสดงการเชื่อมต่อล้มเหลวและลองใหม่แบบถอยเวลา |
| `…?mode=invalid` | ค่าไม่ถูกต้อง → ถูกปฏิเสธ ค่าที่ถูกต้องล่าสุดยังอยู่ แสดง "ข้อมูลไม่ถูกต้อง" |
| `…?mode=high` | ระดับบ่อสูบน้ำสูง → เกิดการแจ้งเตือน |

fixture นี้เป็นเพียงข้อมูลทดสอบ **ไม่ใช่การเชื่อมต่ออุปกรณ์ของฟอร์จูน**

## สถานการณ์ตัวอย่าง (เดโม)

แถบเดโมด้านบนมี: เลือกสถานการณ์, ความเร็วจำลอง (1×, 10×, 60×), เวลาเริ่มสถานการณ์ และ **เวลาจำลอง** (ปุ่มความเร็วไม่แสดงในโหมด API)

| สถานการณ์ | จุดที่ได้รับผล | ผลที่คาดหวัง (ตามเวลาจำลอง) |
|---|---|---|
| ทำงานปกติ | — | ค่าทุกจุดอยู่ในช่วงปกติ |
| ระดับบ่อสูบน้ำสูงขึ้น | P-001 | +6 cm/นาที → เตือน ~10 นาที, วิกฤต ~15 นาที |
| ระดับถังเก็บน้ำต่ำ | P-002 | −4 %/นาที → เตือน ~9 นาที, วิกฤต ~13 นาที |
| ห้องไฟฟ้าอุณหภูมิสูง | P-007 | +0.9 °C/นาที → เตือน ~5 นาที, วิกฤต ~8 นาที |
| ตรวจพบน้ำรั่ว | P-008 | เปลี่ยนเป็น "เปียก" หลัง 1 นาที → วิกฤตทันที |
| อุปกรณ์ขาดการติดต่อ | เลือกจุดได้ (ค่าเริ่มต้น P-005) | จุดนั้นหยุดส่งค่า → "ข้อมูลเก่า" หลัง 120 วินาที |

ค่าทุกค่าเป็นฟังก์ชันของ seed + จุด + เวลา + สถานการณ์ (deterministic) ได้ผลเหมือนเดิมทุกครั้ง เวลาและ seed ถูกส่งเข้า (inject) ไม่ได้ซ่อนใน global

**ลองตามลำดับนี้:** เลือก "ตรวจพบน้ำรั่ว" + ความเร็ว 60× → ภายในไม่กี่วินาที จุด 8 เป็นสีแดง KPI จุดวิกฤต = 1 → เปิดเมนูแจ้งเตือน ใส่ชื่อและบันทึกแล้วกด "รับทราบ" (ยังแสดง "ยังเกิดอยู่") → เปลี่ยนกลับเป็น "ทำงานปกติ" → เหตุการณ์เปลี่ยนเป็น "กลับสู่ปกติแล้ว" แยกจากการรับทราบ

**รีเซ็ตข้อมูลจำลอง** ลบเฉพาะประวัติและเหตุการณ์ของแหล่ง demo (ข้อมูลจาก API ไม่ถูกแตะต้อง) เมื่อเริ่มเดโมครั้งแรกจะสร้างประวัติ *จำลอง* ย้อนหลัง 30 นาทีเพื่อให้กราฟมีข้อมูล หากปิดแอปไว้นานกว่านั้นช่วงที่ขาดจะเว้นว่างในกราฟ

แอนิเมชันระดับน้ำในถัง (P-002) และใบพัดปั๊ม (P-003) ในโมเดล 3D เคลื่อนไหว **เฉพาะเมื่อได้รับค่าที่สดใหม่** ของค่าวัดนั้น ไม่ใช่การยืนยันสภาพเครื่องจักร ปั๊มหยุดหรือกระแส 0 A ไม่ถือว่าเครื่องเสีย

## มุมมองชั้นเดี่ยวและกติกาชั้น/การเลือกจุด

**เลือกชั้น** จากรายการ "ชั้น" (หรือปุ่ม "แยกชั้นที่เลือก") → ชั้นนั้นถูกแยกออกเป็นโมเดลเดี่ยวทันที:
- เลื่อนทั้งชั้น (แผ่นพื้น ผัง อุปกรณ์ หมุด) มากลางฐานโมเดลด้วยค่าเลื่อนเดียวกัน หมุดจึงอยู่ตำแหน่งเดิมเมื่อเทียบกับผัง
- ซ่อนชั้นและส่วนอาคารอื่นทั้งหมด คงโต๊ะและห้องทดลองไว้ กล้องปรับให้เห็นทั้งชั้นพอดี ยังหมุน/ซูมได้
- ป้าย **"กำลังดู: ชั้น …"** บนพื้นที่แสดงผล และปุ่ม **"กลับไปดูทั้งอาคาร"** ประกอบทุกชั้นกลับตำแหน่งเดิม
- ใช้ได้ทุกชั้น: G, 1–5 และสำนักงาน **ชั้น 11, 12 … 31 แยกเป็นตัวเลือกรายชั้น** ทุกชั้นสำนักงานใช้ "ผังอ้างอิงร่วม" ภาพเดียวกัน แต่จุดตรวจวัดและข้อมูลเซนเซอร์ผูกกับชั้นของตัวเอง (ตัวอย่าง: P-004 ชั้น 11, P-007 ชั้น 12) ไม่มีการคัดลอก/ย้ายจุดไปชั้นอื่น ชั้นที่ไม่มีจุดแสดง "ยังไม่มีจุดตรวจวัดในชั้นนี้"

**กติกาเดียว (src/domain/viewState.js) ใช้กับทุกเส้นทาง** — dropdown, ผัง 2D, หมุด 3D, ตาราง, แจ้งเตือน, toast, รีเฟรชหน้า, แก้การตั้งค่า:
1. มุมมองชั้นเดียว = แยกชั้นใน 3D หรือผัง 2D → dropdown ป้าย โมเดล ผัง หมุด และรายการจุดในหน้าภาพรวม ใช้ชั้นเดียวกัน
2. ถ้าจุดที่เลือกไม่อยู่บนชั้นที่กำลังดู → ล้างการเลือกทันที (รายละเอียด กราฟ ไฮไลต์)
3. คลิกแจ้งเตือน/"เปิดชั้นที่เกิดเหตุ" → ไปชั้นจริงของจุด เลือก และซูมที่จุด
4. ค่าที่บันทึกไว้ไม่สอดคล้อง (เช่น ชั้นไม่มีอยู่ หรือจุดอยู่คนละชั้น) ถูกแก้ตอนเปิดแอป

หน้า "จุดตรวจวัด" ยังกรองชั้นได้อิสระ (ไม่ผูกกับชั้นที่กำลังดูในภาพรวม)

**ย้ายข้อมูลรุ่นเดิม:** การตั้งค่า/ไฟล์สำรองรุ่น 1 (ชั้นสำนักงานเดียว "OF") ถูกแปลงอัตโนมัติ — P-004 → ชั้น 11, P-007 → ชั้น 12, จุดอื่นบน OF → ชั้น 11 (ไม่คัดลอก) ประวัติค่าวัดและการแจ้งเตือนใช้ต่อได้

**ตรวจรายชั้นในเบราว์เซอร์:** `python scripts/e2e_floors.py http://localhost:4173 ผลลัพธ์` สร้าง `floor-check.md` (ตารางผลทุกชั้น ทั้ง 3D และ 2D) ผลล่าสุดอยู่ที่ `docs/floor-check.md`


## เว็บไซต์ 3 มิติ: ใช้งาน แก้ไข และเผยแพร่

**ใช้งาน (หน้า "ภาพรวม" → โมเดล 3D)**
- เปิดเว็บแล้วมีหน้าจอ Loading จนโมเดลห้องของชั้นที่ลิฟต์จอดพร้อม ชั้นอื่นโหลดต่อเบื้องหลัง (ป้าย "กำลังดู" แสดงจำนวนชั้นที่โหลดแล้ว)
- เมาส์: ลากซ้าย = หมุน · ลากขวา/Shift+ลาก = เลื่อน · ล้อ = ซูม · จอสัมผัส: นิ้วเดียว = หมุน · สองนิ้ว = ซูม/เลื่อน
- เลือกชั้น: ปุ่ม **ทั้งอาคาร / G / 1 / 2 / 3 / 4 / 5** หรือรายการ "ชั้น" (รวมสำนักงาน 11–32) · **⟲ รีเซ็ตมุมกล้อง** · **⛶ เต็มจอ** (มุมขวาล่างของโมเดล)
- ลิฟต์: แผง "ลิฟต์โดยสาร L1" กดชั้น G/1/2/3 (ดูหัวข้อลิฟต์)
- กดห้อง/พื้นที่ในโมเดล → การ์ดข้อมูล: ชื่อ ชั้น ประเภทพื้นที่ พื้นที่โดยประมาณ (ตร.ม.) จุดตรวจวัด IoT ในพื้นที่ หมายเหตุจากไฟล์โมเดล และ **ภาพจากผังต้นฉบับ** ของพื้นที่นั้น (เลขห้อง/ชื่อร้านที่พิมพ์ในผังยังเป็นภาพในโมเดล ไม่ได้ถอดเป็นข้อความ จึงไม่เดาเลข)
  ข้อมูลห้องส่งออกจากไฟล์ .blend ด้วย `scripts/blender/export_rooms.py` → `public/models/floors/rooms-<ชั้น>.json`

**แก้ไขแล้วเผยแพร่ครั้งถัดไป**
```bash
npm install                 # ครั้งแรก
npm run dev                 # แก้ไขและดูผลที่ http://localhost:5173
npm test && npm run build   # ทดสอบ + สร้างเว็บฉบับ Production ใน dist/
npm run preview             # ตรวจ dist/ ที่ http://localhost:4173
npm run deploy              # อัปโหลด dist/ ขึ้น GitHub Pages (สาขา gh-pages)
```
- แก้โมเดลใน Blender แล้วส่งออกใหม่: `python scripts/blender/export_user_floors.py <models> public/models/floors` และ `python scripts/blender/export_rooms.py <models> public/models/floors` (ต้องมีโมดูล `bpy`) แล้ว build/deploy ตามด้านบน
- GitHub Pages: Settings → Pages → Source = **Deploy from a branch**, Branch = **gh-pages** / **(root)** (ตั้งครั้งเดียว) ลิงก์: `https://poyspoy.github.io/iot-fortune-v2/`

## โมเดลรายชั้นจาก Blender

ทุกชั้นที่มีไฟล์ (G, 1–5 และสำนักงาน 11–31) แสดงเป็นห้อง 3 มิติจากโมเดล Blender ของผู้ใช้ (`Fortune_<ชั้น>_v2.blend` → `public/models/floors/floor-<ชั้น>.glb`) ทั้งในมุมมอง **ทั้งอาคาร** (เรียงซ้อนตามระดับชั้น) และมุมมองชั้นเดี่ยว — รายการไฟล์ที่ตรวจแล้วอยู่ที่ `docs/models-inventory.md`
- มุมมองทั้งอาคารโหลดทีละ 2 ไฟล์ (ชั้นที่ลิฟต์จอดก่อน) ป้าย "กำลังดู" แสดงความคืบหน้า · จอเล็ก (≤ 760 px) โหลดเฉพาะชั้นห้าง ชั้นสำนักงานโหลดเมื่อแยกดูชั้น
- ตอนโหลด ชิ้นส่วนที่ค่าวัสดุเหมือนกันถูกรวมเป็นก้อนเดียว และสีล้วนของแต่ละชิ้นเก็บไว้ที่จุดยอด (ค่าสีเดิมทุกประการ) — จำนวนการวาดต่อเฟรมทั้งอาคารลดจาก ~6,800 เหลือ ~140 โดยรูปทรงและสีไม่เปลี่ยน (`src/scene/detailModel.js`)
- พื้นโมเดล (Z = 0 ใน Blender) วางตรงระดับพื้นชั้น = ระดับที่ลิฟต์จอด (ทดสอบใน `scripts/e2e_elevator.py`)
- ไม่แก้รูปทรง สี ป้าย หรือสัญลักษณ์ — ส่งออกเฉพาะวัตถุที่แสดงผล (ไม่รวมคอลเลกชัน Reference/Presentation)
- วางด้วยสูตรพิกัดเดียวกับสคริปต์ที่สร้างโมเดล (`detailTransform` ใน `src/domain/geometry.js`) จุดตรวจวัดจึงตรงตำแหน่งบนโมเดลทุกชั้น (มีชุดทดสอบใน `tests/floors.test.js`)
- ป้ายบนแผงบอกสถานะ: กำลังโหลด / โมเดลจาก Blender ของคุณ / โหลดไม่ได้ (ใช้โมเดลแบบง่าย) / ชั้นนี้ยังไม่มีโมเดล (ชั้น 32)
- ส่งออกใหม่: `python scripts/blender/export_user_floors.py <โฟลเดอร์ models> public/models/floors` (ต้องมีโมดูล `bpy`)

## ลิฟต์ 3 มิติ (จำลอง)

**จำลองการทำงานเท่านั้น ไม่ได้เชื่อมข้อมูลลิฟต์จริง** แสดงในมุมมอง "ทั้งอาคาร" ของโมเดล 3D (แผง "ลิฟต์โดยสาร L1" มุมขวาล่าง)

**ลองใช้:** เปิดแอป → ภาพรวม → โมเดล 3D → กด **"มุมกล้องลิฟต์"** หรือ **"เปิดปล่อง"** → กดปุ่มชั้น **G / 1 / 2 / 3**
- ลำดับทุกครั้ง: ประตูปิด → ห้องลิฟต์ค่อย ๆ ออกตัวและชะลอก่อนหยุด → หยุดเมื่อพื้นห้องลิฟต์ตรงพื้นชั้น → ประตูเปิด
- ประตูสองบานเป็นส่วนของห้องลิฟต์ (เคลื่อนตามกัน) ปล่องอยู่กับที่
- ระหว่างเดินทางปุ่มชั้นถูกปิดชั่วคราว แผงแสดงชั้นปลายทางและลูกศร ▲/▼ เมื่อถึงแสดง "ถึงชั้น …" และสถานะประตู
- กดชั้นที่ลิฟต์จอดอยู่ → ไม่เดินทางใหม่
- เชื่อมกับการเลือกชั้นเดิม: ชั้นที่ลิฟต์ถึงกลายเป็น "ชั้นที่เลือก" (ขอบ/ป้ายชั้นในโมเดล) ปุ่ม **"แยกดูชั้น …"** เปิดมุมมองชั้นเดี่ยวเดิม ในมุมมองชั้นเดี่ยวลิฟต์ถูกซ่อน (ใช้สัญลักษณ์ลิฟต์ในโมเดลของผู้ใช้) และมีปุ่ม "ดูลิฟต์" กลับมาทั้งอาคาร
- "เปิดปล่อง" = ระนาบตัดหน้าตัดอาคารห้างที่ด้านหน้าปล่อง ให้เห็นห้องลิฟต์และห้อง/ผนัง/ทางเดินของโมเดลเดิมเป็นภาพตัด (ไม่เปลี่ยนสี/รูปทรง เพียงไม่วาดส่วนหน้าปล่อง) ทำงานได้ทั้งโหมดภายนอก ตัดชั้นบน และแยกชั้น

**ตำแหน่งและชั้นที่จอด:** อ้างอิงสัญลักษณ์ลิฟต์ในโมเดล Blender/ผังต้นฉบับ — โถงลิฟต์กลางห้างพบในผังชั้น G, 1, 2, 3 ใกล้กัน (ต่างกันไม่เกิน ~2 ม.) จึงวางปล่องที่ค่าเฉลี่ย และให้จอด G–3
ชั้น 4 และ 5 ไม่มีสัญลักษณ์ลิฟต์ที่ตำแหน่งนี้ จึงยังไม่จอด · ทิศประตูไม่ระบุในผัง (สมมติหันด้านหน้าโมเดล) · ขนาดปล่อง/ห้องลิฟต์เป็นค่าประมาณ

**โค้ด:** `src/domain/elevator.js` (ลำดับการทำงาน/เวลา — ทดสอบใน Node), `src/scene/elevator3d.js` (ปล่อง ห้องลิฟต์ ประตู), `src/ui/elevatorPanel.js` (แผงควบคุม)
ปรับเวลา: `ELEVATOR_TIMING` (ปิด/เปิดประตู 1.4 วินาที, 1.5 วินาทีต่อชั้น) · เพิ่ม/ย้ายลิฟต์: `ELEVATOR_L1` (ชั้นที่จอด ตำแหน่ง ขนาด)

**ทดสอบ:** `npm test` (tests/elevator.test.js) และในเบราว์เซอร์ `python scripts/e2e_elevator.py http://localhost:4173 ผลลัพธ์`
บันทึกคลิป: `python scripts/record_elevator_clip.py http://localhost:4173 ผลลัพธ์ 15` (ต้องมี ffmpeg)

## การวางและตั้งค่าจุด

**ตั้งค่าจุด → จุดตรวจวัด → + เพิ่มจุด** หรือ "แก้ไข" ที่จุดเดิม

- **รหัสจุด** คงที่หลังสร้าง (ใช้เชื่อมกับประวัติ)
- **รหัสอ้างอิงต้นทาง** (`sourceKey`) = `pointId` ที่ API ส่งมา ถ้าไม่ตรงกับรหัสจุด ค่าเริ่มต้นคือรหัสจุด ค่าวัดก็มี `sourceKey` ของตัวเองเช่นกัน
- **ตำแหน่ง:** คลิกบนผังชั้นในฟอร์ม หรือพิมพ์พิกัด x, y (0–1 นับจากซ้าย/บนของภาพผัง) พิกัดนี้เป็นตำแหน่งสัมพัทธ์บนภาพ **ไม่ใช่พิกัดสำรวจจริง**
- **พิกัด 3D เอง (ไม่บังคับ):** ระบบตรวจว่าอยู่ในกรอบของชั้นนั้น (แสดงขอบเขตในฟอร์ม)
- **ค่าวัด:** ตัวเลข (ต้องมีหน่วย, ช่วงค่าที่เป็นไปได้, ทศนิยม) หรือสถานะ (`ค่า:ชื่อ` คั่นจุลภาค เช่น `dry:แห้ง, wet:เปียก`) และเวลาที่ถือว่าข้อมูลเก่า หน่วยต่างกันให้แยกค่าวัด (เช่น kW กับ kWh)
- ลบ/เปลี่ยนรหัสค่าวัดที่มีอยู่ไม่ได้ (เพื่อรักษาประวัติ) — ให้ **เก็บถาวร** จุดแล้วสร้างใหม่ จุดเก็บถาวรไม่ถูกติดตาม ไม่นับ KPI แต่ประวัติยังอยู่
- การแปลงหน่วยกำหนดได้ในไฟล์ตั้งค่า (`unitConversions`, ตัวอย่าง P-001 รับ `mm` แปลงเป็น `cm`)
- ผลการบันทึกแสดงตามจริง: ถ้าตรวจไม่ผ่านจะบอกรายการที่ต้องแก้ ถ้าบันทึกลงเครื่องไม่ได้จะไม่แสดง "บันทึกแล้ว"

## สัญญา HTTP (Telemetry contract)

แอปส่ง `GET` ไปยัง URL ที่ตั้งไว้ (ไม่ส่ง cookie: `credentials: 'omit'`, `Accept: application/json`, `cache: no-store`) และคาดหวัง:

```json
{
  "schemaVersion": 1,
  "samples": [
    {
      "pointId": "P-001",
      "metricId": "level",
      "value": 42.5,
      "unit": "cm",
      "observedAt": "2026-10-14T03:00:00Z",
      "quality": "good",
      "sequence": 101
    }
  ]
}
```

| ฟิลด์ | กติกา |
|---|---|
| `schemaVersion` | ต้องเป็น `1` |
| `pointId` / `metricId` | ตรงกับ `sourceKey` ของจุด/ค่าวัด และจุดต้อง active |
| `value` | ตัวเลข: `number` ที่ finite เท่านั้น (ไม่รับ `"42"`, `NaN`) **ค่า 0 ถูกต้อง** / สถานะ: ข้อความที่อยู่ในรายการสถานะ |
| `unit` | ต้องตรงกับหน่วยที่ตั้งไว้ หรือมีการแปลงหน่วยกำหนดไว้ สถานะส่ง `""` หรือไม่ส่ง |
| `observedAt` | ISO-8601 พร้อมเขตเวลา (`Z` หรือ `+07:00`) — **เวลาที่เซนเซอร์วัด** ไม่ใช่เวลาที่ส่ง |
| `quality` | `good` / `uncertain` / `bad` — ไม่ส่งถือเป็น `uncertain`; `bad` ถูกปฏิเสธ |
| `sequence` | จำนวนเต็มไม่ติดลบ (ไม่บังคับ) เพิ่มขึ้นต่อค่าวัด |

ค่าที่อยู่นอกช่วง `plausible` ถูกปฏิเสธ, เวลาที่ล้ำอนาคตเกิน **60 วินาที** ถูกปฏิเสธ

**การตัดค่าซ้ำและลำดับ (ต่อหนึ่งค่าวัด หลังเรียงชุดข้อมูลตาม observedAt, sequence):**
- `observedAt` เท่ากับค่าล่าสุด และ (`sequence` เท่ากัน หรือ ค่าเท่ากัน) → **ซ้ำ** ข้ามไป ไม่นับเป็นการสังเกตใหม่ (poll ซ้ำได้ค่าเดิมจึงไม่ทำให้ข้อมูลสดใหม่ และไม่นับเวลาคงค่า)
- `observedAt` เท่ากันแต่ค่าต่างกัน → ปฏิเสธ (conflict)
- `observedAt` เก่ากว่าค่าล่าสุด หรือ `sequence` ไม่เพิ่มขึ้น → ปฏิเสธ (out-of-order) **ไม่เขียนทับค่าใหม่กว่า**

ค่าที่ถูกปฏิเสธนับตามเหตุผลและแสดงในเมนู **ประวัติข้อมูล → การตรวจข้อมูลที่รับเข้า** (นับตั้งแต่เปิดแอป)

**การ poll:** ค่าเริ่มต้นทุก 10 วินาที (ตั้งได้ 5–3600), timeout ด้วย AbortController (ค่าเริ่มต้น 8 วินาที), ไม่ poll ซ้อน, ล้มเหลวแล้วถอยเวลา `interval × 2^n` สูงสุด 5 นาที, เปลี่ยน URL/แหล่งข้อมูลแล้วยกเลิกคำขอเก่าและทิ้งคำตอบที่มาช้า แถบสถานะแสดง "poll สำเร็จล่าสุด / ล้มเหลวล่าสุด / ลองใหม่ใน …" **แยกจากความสดของค่าวัด**

## CORS และความปลอดภัย

- URL ต้องเป็น **HTTPS** (อนุญาต `http://localhost`, `127.0.0.1`, `[::1]`, `*.localhost` สำหรับพัฒนา)
- เซิร์ฟเวอร์ต้องตอบ header CORS เช่น
  ```
  Access-Control-Allow-Origin: https://โดเมนที่วางแอป
  Access-Control-Allow-Methods: GET
  ```
  ถ้าไม่มี เบราว์เซอร์จะบล็อก และแอปแสดง "เชื่อมต่อไม่ได้ (เครือข่ายหรือ CORS)"
- **ห้าม** ใส่รหัสผ่าน API key token ถาวร หรือรหัส MQTT broker ในแอปนี้หรือใน URL (แอปปฏิเสธ URL ที่มี user:password) ข้อมูลที่ต้องยืนยันตัวตนให้ผ่านบริการฝั่งเซิร์ฟเวอร์ (proxy) ที่ดูแลสิทธิ์และเปิดเฉพาะ endpoint อ่านอย่างเดียว
- แอปเรียกเฉพาะ URL ที่ตั้งไว้ ไม่ค้นหาอุปกรณ์ ไม่สแกนเครือข่าย ไม่เชื่อม MQTT โดยตรง
- ชื่อ/บันทึกที่ผู้ใช้พิมพ์แสดงเป็นข้อความธรรมดาเสมอ (ไม่ใช้ innerHTML)

## คุณภาพข้อมูลและกฎการแจ้งเตือน

### คุณภาพข้อมูล (ประเมินแยกทีละค่าวัด)
| สถานะ | เงื่อนไข |
|---|---|
| สดใหม่ | อายุ (เวลาปัจจุบัน − **observedAt**) ≤ เวลาหมดอายุของค่าวัด |
| ข้อมูลเก่า | อายุเกินเวลาหมดอายุ |
| ยังไม่มีข้อมูล | ยังไม่เคยได้รับค่าที่ถูกต้อง |
| ข้อมูลไม่ถูกต้อง | ค่าที่ได้รับล่าสุด (ใหม่กว่าค่าที่ถูกต้องล่าสุด) ถูกปฏิเสธ — ยังแสดงค่าที่ถูกต้องล่าสุดและอายุของมัน |

สถานะการเชื่อมต่อ (poll สำเร็จ/ล้มเหลว) แสดงแยกบนแถบด้านบน **poll สำเร็จไม่ทำให้ค่าเก่าสดใหม่**

### กฎ
- **ค่าสูง** (high), **ค่าต่ำ** (low), **ช่วงที่ยอมรับ** (range), **สถานะ** (discrete) แต่ละกฎมีค่าเตือน/วิกฤต ฮิสเทอรีซิส เวลาคงค่า (dwell) และเปิด/ปิดได้ — ทุกค่าเริ่มต้นติดป้าย **"เกณฑ์ตัวอย่าง — รออนุมัติสำหรับอุปกรณ์จริง"**
- **ขอบเขต (inclusive):** ค่าเท่ากับขีดพอดีถือว่าถึงขีด (high: `v ≥ ขีด`, low: `v ≤ ขีด`)
- **ฮิสเทอรีซิส h:** ลดระดับ/กลับสู่ปกติเมื่อพ้นขีดแบบเคร่งครัด (high: `v < ขีด − h`, low: `v > ขีด + h`) ทั้งระดับเตือนและวิกฤต
- **เวลาคงค่า:** ต้องมีค่าที่ถูกต้องเกินขีดต่อเนื่องนาน ≥ dwell (นับจาก observedAt) จึงเปิด/ยกระดับ ช่องว่างระหว่างค่าที่นานกว่าเวลาหมดอายุ หรือข้อมูลกลายเป็นเก่า/ไม่ถูกต้อง จะ **ล้างการนับ** การไม่มีข้อมูลยืนยันการเกินขีดไม่ได้
- **ข้อมูลเก่า/ไม่ถูกต้อง/ไม่มีข้อมูล ไม่ถือเป็นค่าปกติ ค่า 0 หรือการฟื้นตัว** การแจ้งเตือนที่เกิดอยู่ยังคงอยู่จนกว่าจะมีค่าที่ถูกต้องพ้นเกณฑ์
- **เหตุการณ์ (episode)** หนึ่งต่อ จุด+ค่าวัด+กฎ ต่อเนื่อง การยกระดับเตือน→วิกฤตอัปเดตเหตุการณ์เดิม ไม่สร้างใหม่ทุก poll กลับสู่ปกติแล้วเกินขีดอีกจะเป็นเหตุการณ์ใหม่
- **รับทราบ ≠ กลับสู่ปกติ:** สถานะ "เกิดอยู่/กลับสู่ปกติ" กับ "รับทราบ/ยังไม่รับทราบ" แยกกัน รับทราบเหตุการณ์ที่กลับสู่ปกติแล้วได้โดยไม่เปลี่ยนประวัติ ถ้ารับทราบที่ระดับเตือนแล้วยกระดับเป็นวิกฤต ต้องรับทราบใหม่ ชื่อผู้รับทราบเป็นป้ายชื่อในเครื่อง ไม่ใช่การยืนยันตัวตน
- **เปลี่ยนเกณฑ์** มีผลทันทีกับค่าที่สดใหม่อยู่ (ประเมินใหม่ทันที) แต่กราฟประวัติเปลี่ยนเมื่อมีค่าใหม่เท่านั้น ปิดกฎระหว่างเกิดเหตุ = ยุติด้วยเหตุผล "ปิดกฎ" (ไม่ใช่การกลับสู่ปกติ)
- สรุประดับของจุดแบบระมัดระวัง: ระดับสูงสุดของทุกค่าวัด และคุณภาพแย่ที่สุด แสดงป้ายระดับคู่กับป้ายคุณภาพเสมอ
- **เสียงเตือน** ปิดเป็นค่าเริ่มต้น เปิดได้ที่ปุ่มมุมขวาบน ทำงานเฉพาะขณะเปิดหน้านี้ การปิดเสียงไม่ซ่อนการแจ้งเตือนในรายการหรือบนผัง ไม่มีการส่ง LINE/อีเมล
- dwell ที่กำลังนับอยู่ไม่ถูกบันทึกลงเครื่อง (รีโหลดแล้วเริ่มนับใหม่) ส่วนเหตุการณ์ที่เกิดแล้วถูกบันทึก

## การเก็บข้อมูลในเครื่องและนโยบายเก็บย้อนหลัง

- เก็บใน **IndexedDB** ของเบราว์เซอร์/โปรไฟล์นี้เท่านั้น: การตั้งค่าจุดและเกณฑ์, ค่าที่ได้รับ, เหตุการณ์แจ้งเตือนและการรับทราบ, การตั้งค่าแหล่งข้อมูล, การตั้งค่าหน้าจอ
- ไม่ซิงก์ระหว่างเครื่องหรือผู้ปฏิบัติงาน การล้างข้อมูลเว็บไซต์จะลบทั้งหมด → สำรองเป็นไฟล์เป็นระยะ
- เวลาเก็บเป็น UTC แสดงผลเป็นเวลาไทย (Asia/Bangkok)
- **นโยบาย (ค่าเริ่มต้น):** เก็บ **7 วัน หรือ 100,000 ค่า แล้วแต่ถึงก่อน** ลบค่าที่ observedAt เก่ากว่า 7 วันก่อน แล้วถ้ายังเกินจำนวน ลบค่าที่ observedAt เก่าที่สุด (ทุกแหล่งรวมกัน) ตรวจไม่เกินนาทีละครั้ง ตั้งได้ 1–30 วัน / 1,000–500,000 ค่า
- ถ้าพื้นที่เต็มหรือบันทึกไม่สำเร็จ แสดงแถบสีแดงชัดเจน และไม่แสดง "บันทึกแล้ว"
- กราฟแสดง "ประวัติที่บันทึกในอุปกรณ์นี้" ช่วงที่ไม่มีข้อมูลแรเงาเทาและไม่ลากเส้นข้าม ไม่มีการเติมค่าย้อนหลังจาก API

## สำรองและกู้คืน

**ตั้งค่าจุด → การเก็บข้อมูลและสำรองข้อมูล**
- **ส่งออกสำรอง (JSON):** การตั้งค่า, ค่าที่เก็บทั้งหมด (ทุกแหล่ง), เหตุการณ์แจ้งเตือน และการตั้งค่าแหล่งข้อมูล
- **นำเข้า:** ตรวจทั้งไฟล์ก่อนเขียน (รูปแบบ, schema, การอ้างอิงจุด/ค่าวัด/กฎ, รหัสซ้ำ) → แสดงตัวอย่างสรุป → ต้องกด "ยืนยัน: แทนที่ข้อมูลทั้งหมด" → เขียนใน transaction เดียว ถ้าล้มเหลวข้อมูลเดิมยังอยู่ครบ
- เวลาสังเกตเดิมคงอยู่ ความสดใหม่คำนวณใหม่ตามเวลาปัจจุบัน (ค่าเก่ายังเป็นค่าเก่า)
- **CSV:** เมนูประวัติข้อมูล ส่งออกค่าวัด (ช่วงเวลาที่เลือก) และการแจ้งเตือน มีเวลา UTC และเวลาไทย มี BOM สำหรับ Excel ภาษาไทย ข้อความที่ขึ้นต้นด้วย `= + - @` ถูกเติม `'` นำหน้าเพื่อไม่ให้กลายเป็นสูตร

## เปลี่ยนผังอ้างอิง/แบบจำลองอาคาร

ข้อมูลอาคารอยู่ใน `src/domain/defaultConfig.js` และภาพผังใน `public/plans/`

1. ครอปภาพผังแต่ละชั้นให้พอดีกรอบอาคาร บันทึกเป็น `public/plans/floor-<รหัสชั้น>.webp` (ขนาดกว้าง ~2400 px)
2. แก้ `plan.width/height` ให้ตรงขนาดภาพ
3. ลากรูปทรงอาคาร `footprint` เป็นพิกัดปกติ 0–1 ของภาพที่ครอป (ตามเข็มนาฬิกาหรือทวนก็ได้)
4. `model` กำหนดกรอบในโลก 3D: `cx, cz` (ศูนย์กลาง), `width, depth` (สัดส่วนควรตรงภาพ), `elevation` (ความสูงชั้น), `height`
5. พื้นที่ (`areas`) ระบุชนิด `sales | service | plant | electrical | parking | roof | underfloor` — ปุ่มมุมกล้อง "ห้องเครื่อง / ดาดฟ้า / ระบบใต้พื้น" **แสดงเฉพาะเมื่อมีพื้นที่ชนิดนั้นและมีจุดอยู่** (ปัจจุบันมีเฉพาะ "ห้องเครื่อง" จากห้อง AHU ในผังสำนักงาน)
6. ข้อมูลที่ยังไม่ยืนยันให้ระบุใน `referenceNote` / `plan.note` ซึ่งแสดงบนหน้าจอ

ข้อมูลที่ใช้ตอนนี้: ผังชั้น G, 1, 2, 3, 4, 5 และผังสำนักงานชั้น 11–31 ที่ผู้ใช้แนบมา (ใช้เป็นผังอ้างอิงร่วมของชั้น 11 … 31 ซึ่งแยกเป็นชั้นละรายการ — เมื่อได้ผังจริงรายชั้น ให้แก้ `plan` ของชั้นนั้นใน `towerFloors()`) ผังชั้น 4 วาดคนละสเกล จึงยืดเข้ากรอบเดียวกันโดยประมาณ, ผังชั้น 5 ไม่ตามสเกล, ตำแหน่งทาวเวอร์บนโต๊ะไม่ใช่ตำแหน่งจริง, ชั้น 6–10 ไม่มีผังจึงไม่ได้สร้าง ถ้าเปลี่ยนการตั้งค่าเริ่มต้นแล้วต้องการให้เครื่องที่ใช้อยู่ได้ค่าใหม่ ใช้ปุ่ม "คืนค่าการตั้งค่าจุดเริ่มต้น" (ประวัติไม่ถูกลบ, จุดที่เพิ่มเองถูกเก็บถาวรไว้)

โลโก้: ปัจจุบันใช้ข้อความ "NEXZA | FORTUNE IoT" เมื่อได้โลโก้ที่ได้รับอนุญาต ให้ใส่ไฟล์ใน `public/` แล้วแทนข้อความใน `src/ui/app.js` (ส่วน `brand`) โดยไม่แก้ไขตัวโลโก้

## การเชื่อมต่อ backend ในอนาคต

โค้ดแยกชั้นไว้ให้เปลี่ยนส่วนหลังบ้านได้:

| ชั้น | ไฟล์ | เปลี่ยนเป็น |

## ข้อจำกัด

- เป็นต้นแบบฝั่งหน้าเว็บ: การดึงข้อมูล ประเมินแจ้งเตือน และเสียง ทำงานเฉพาะขณะเปิดหน้าเว็บ **ไม่ใช่การเฝ้าระวัง 24 ชั่วโมง**
- ข้อมูลและการรับทราบอยู่ในเบราว์เซอร์เครื่องเดียว ไม่ซิงก์ระหว่างผู้ปฏิบัติงาน ชื่อผู้รับทราบไม่ใช่การยืนยันตัวตน
- จุด IoT, ตำแหน่ง, และเกณฑ์ทั้งหมดเป็นตัวอย่าง ยังไม่ได้รับรายการอุปกรณ์จริงหรือ API จริง
- รูปทรงอาคาร 3D ลากจากผังพื้นที่เช่าโดยประมาณ ไม่ใช่แบบก่อสร้าง ไม่มีข้อมูลห้องเครื่อง/ดาดฟ้า/ใต้พื้นจริง
- การนับ dwell ที่ค้างอยู่หายเมื่อรีโหลด, สถิติข้อมูลที่ถูกปฏิเสธนับตั้งแต่เปิดแอป
- โหมด API อ่าน JSON แบบ polling เท่านั้น (ไม่มี WebSocket/MQTT)
